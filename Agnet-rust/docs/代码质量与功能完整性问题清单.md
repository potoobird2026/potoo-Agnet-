## 一、完整执行链路

### 1.1 系统启动流程

```
main.rs 启动
  │
  ├── 读取 config/config.toml
  │   └── toml → serde_json::Value
  │
  ├── 创建 Pipeline（with_recommended_phases）
  │   ├── Phase::init()
  │   ├── Phase::context()
  │   ├── Phase::think()
  │   ├── Phase::audit()
  │   ├── Phase::execute()
  │   ├── Phase::loop_phase()
  │   └── Phase::memorize()
  │
  ├── 注册 8 个 Slot（通过 register_slot 自动 init() + add_slot）
  │   ├── Init → InitPhaseSlot
  │   ├── Context → ToolRegistrySlot
  │   ├── Context → AssemblerSlot（若 enabled）
  │   ├── Think → LlmThinkerSlot
  │   ├── Audit → AuditPhaseSlot
  │   ├── Execute → ToolExecutorSlot
  │   ├── Loop → ReActLoopSlot
  │   └── Memorize → MemorySaverSlot
  │
  ├── 初始化并启动 9 个 Service（手动 init → start）
  │   ├── 每个 Service 在 start() 中向 ProviderRegistry 注册业务 Provider
  │   └── ProviderRegistry 内容：
  │       ├── "llm"                     → DynProvider<dyn LlmContract>
  │       ├── "llm_format_adapter"      → DefaultFormatAdapter
  │       ├── "memory"                  → MemoryService (impl MemoryProvider)
  │       ├── "tools"                   → ToolsService (impl ToolProvider)

  │       ├── "compression_summary"     → DynProvider(CompressionSummaryContract)
  │       └── "chronos"                 → Arc::new(())  ← 占位符
  │
  └── runtime.step("session-1", "你好")
```

## 三、全局架构问题（G 类）

### G1 — CompressionService 的 shared_store 从未连接

**严重度**：🔴 P0

**文件**：`src/plugins/services/compression/service.rs`

**运行逻辑**：

```
// init() 第 81 行
shared_store: None,  ← 永远为 None

// start() 第 89-106 行
→ 注册 CompressionSummaryContract（但 summary 也从 shared_store 读，也是 None）
→ tokio::spawn(run_loop)

// run_loop() 第 133-271 行——代码逻辑完整但不被执行
收到 NewMessagesArrived → state = Compressing
  → if let Some(store) = &inner.shared_store  ← None，跳转到 state = Sleep
  → tracing::warn!("shared_store 未设置，跳过压缩")
```

**实际上 run_loop 中的压缩管道代码（第 151-258 行）是完整的**：
1. 从 shared_store 读消息
2. TokenCounter::count() 计数
3. PidController::update() 计算目标保留比例
4. Anchor::calculate() 计算锚点范围
5. EntityExtractor::extract() + Entropy::calculate()
6. Scorer::score() 逐条评分 + UcbDecision::decide() 保留决策
7. 确保至少 target_keep 条
8. **Compressor::compress() 执行压缩**
9. CAS 写回 shared_store

**所有组件实例化但空转**：PidController、TokenCounter、Anchor、EntityExtractor、Entropy、Scorer、UcbDecision、FuzzyControl、Compressor、Feedback、Recall、Journal —— 共 12 个组件。

**功能影响**：
- `CompressionSummaryContract::get_summary()` 返回 `None`（因为 shared_store 也是 None）
- Assembler 的 `CompressionSummaryProvider` 始终返回空（因为 provider_raw("compression_summary") 读到的 summary 是 None）
- 对话历史永远不会被压缩，长会话的 token 持续增长
- 没有任何运行时错误或 panic——只会静默跳过

**根因**：`main.rs` 创建 `AgentRuntime` 后调 `AgentRuntime::run()`，但 `AgentRuntime` 内部的 `shared_store` 只通过 `Pipeline` 中的 Slot 读写，没有传给 `CompressionService`。`CompressionService` 的设计预期是从外部设置 shared_store，但没有任何代码执行这个设置。

### G2 — Chronos ActionExecutor 的 ExecuteTool 不执行工具

**严重度**：🔴 P0

**文件**：
- `src/plugins/services/chronos/service.rs`（第 97-103 行——注册被注释）

**运行逻辑**：

```
// → orchestrator.entries 始终为空

// chronos/service.rs run_loop() 第 226-286 行
// 注意：run_loop 不调用 orchestrator.process_all()
// 而是直接调用业务 trait 方法（timer, task_queue, state_encoder 等）
// 这绕过了 Component 抽象层，直接调具体实现

// chronos/components/action_executor.rs execute() 第 18-82 行
match decision {
    Decision::Execute { actions } => {
        for action in actions.iter().take(max) {
            match action.action_type {

                    executed += 1;
                }
                ActionType::ExecuteTool => {
                    tracing::info!("执行工具 '{}' (暂为占位)");  // 只打日志

                    executed += 1;
                }
                ActionType::ProactiveMessage => {
                    tracing::info!("主动消息");  // 只打日志

                }
            }
        }

    }

// chronos/orchestrator.rs process_all() 第 45-50 行
pub async fn process_all(&mut self) -> Result<(), ComponentError> {
    let _ = self.entries.len();  // no-op
    Ok(())
}
```

**功能影响**：
- Chronos 定时调度系统**可以正常运行**——它能检测到非活跃会话、触发决策、决定执行动作
- 但实际执行的动作只在日志中记录，**不会对系统产生任何影响**

**根因**：两个层面的问题：

2. ActionExecutor 的 ExecuteTool 路径缺少 ToolProvider 调用（是具体功能的占位符）

### G3 — LlmService 内部三个核心组件从未构造

**严重度**：🟡 P1

**文件**：
- `src/plugins/services/llm/error.rs`（ErrorClassifier——第 17 行）
- `src/plugins/services/llm/formatter.rs`（MultimodalFormatter）
- `src/plugins/services/llm/stream.rs`（StreamProcessor）

**运行逻辑**：

```
LlmContractWrapper::chat() 第 182-240 行
  ├── 合并 config（正常工作）
  ├── self.inner.invoker.invoke()  ← 调用 ChatInvoker（正常工作）
  │   └── ChatInvoker 内部：

  │       ├── 选择 Executor（正常工作）
  │       │   ├── ⚠️ Executor 自己创建 reqwest::Client
  │       │   │   （不使用 LlmService 结构体中的 self.client）
  │       │   ├── ❌ 不构造 ErrorClassifier
  │       │   │   HTTP 400/500 错误没有分类 → 原始字符串错误
  │       │   ├── ❌ 不构造 MultimodalFormatter
  │       │   │   含图片/文件的消息不会格式化 → 只传文本
  │       │   └── ❌ 不构造 StreamProcessor
  │       │       stream=true 时无法解析 SSE 流 → 可能解析失败
  │       └── 执行 HTTP 请求（正常工作）
  └── 返回 ChatResponse（非流模式下正常工作）
```

**功能影响**：
- **非流式文本 LLM 调用完全正常**——这是当前唯一工作的路径
- `ErrorClassifier` 缺失：HTTP 返回 4xx/5xx 时错误消息没有分类，trace_id 和可重试标志丢失
- `MultimodalFormatter` 缺失：多模态消息（携带图片/文件的 ContentBlock）直接以原始格式传递，LLM 端可能无法解析
- `StreamProcessor` 缺失：`config.stream = true` 时流式响应不会被解析，Executor 可能超时或返回空结果

**根因**：三个组件的 struct 和方法完整实现，但 `executors/` 目录下的各 executor 没有实例化和使用它们。这是典型的"组件层级实现但驱动层未串联"模式。

### G4 — main.rs 只有单步执行，无交互循环

**严重度**：🟡 P1

**文件**：`src/main.rs`（第 274-277 行）

**运行逻辑**：

```
// main.rs 第 274-277 行
let result = runtime
    .step(StepInput::new("session-1", "你好，请介绍一下你自己"))
    .await
    .map_err(|e| format!("step 执行失败: {e}"))?;

println!("Step 执行结果: {:#?}", result);
println!("LLM + ReActLoop 模块对接成功。");

// 程序直接退出
```

**问题**：
- CliChannel 已启动，但 `AgentRuntime.run()` 未被调用（用的是 `runtime.step()` 单步方法）
- Pipeline 的 Loop Phase（ReActLoopSlot）从未在集成环境中验证过
- `AgentRuntime.run()` 的主循环（监听 StepInput）从未使用
- `SharedMessageStore` 的 CAS 写入从未经过并发验证

**修复方案**：

**Step 1**: 改 `action_executor.rs`——加字段 + setter + 实现逻辑：

```rust
    }
}

// execute() 中 ExecuteTool 分支改为：

        .and_then(|v| v.as_str()).unwrap_or("unknown");

        .cloned().unwrap_or(serde_json::Value::Null);
```

### 9.3 修复是否会造成软件不可用？

**否**。所有修复遵循以下原则：
1. 不改 `shared_types` 中的 trait 签名——不破坏跨插件契约
2. 不改任何 SlotPlugin/ServicePlugin trait 的方法签名——不破坏插件接口
3. 不改 `StepContext` / `Pipeline` / `AgentRuntime` 的核心执行逻辑
4. 所有修复是**添加行为**（从 no-op 变成有操作），不是**修改行为**

**例外**：Chronos 的 `ActionExecutorService` trait 需要加 `ap: &ServiceAccessPoint` 参数，这会影响该 trait 的签名（但 trait 定义在 Chronos 模块内部，不在 shared_types 中，影响范围仅限于 Chronos 内部）。

### 9.4 修复是否会造成功能缺失？

**否**。修复只会：
- 把 no-op 变成真正执行（Compression 压缩、Chronos 工具调用）
- 把硬编码变成配置驱动（context_window）
- 把占位符变成完整实现（ExecuteTool、RuleLlmSelector）
- 把死代码变成活代码（ErrorClassifier、StreamProcessor）

### 9.5 修复是否存在降级路径？

**部分修复有降级路径**，但不是全部。降级的适用范围：
- **必要降级**：外部依赖可能失败（LLM 网络调用）、配置可能未加载、可选功能未注册
- **无降级/不应降级**：保证存在的 Provider 找不到（表示内部状态异常，应报错不隐瞒）

| 修复 | 降级路径 | 降级后行为 |
|:-----|:---------|:-----------|
| LlmService ErrorClassifier | 构造后条件不满足 → 不使用 | Executor 直接用原始错误消息 |
| RuleLlmSelector LLM/L3 | LLM 调用失败 / MemoryProvider 返回空 | 回退到全部规则（已有 fallback 逻辑） |
| context_window 统一 | `read_context_raw("llm_config")` 返回 None | 继续用 128000 fallback |
| OutputAdapter adapt_system_prompt | `provider_raw("llm_output_adapter")` 返回 None | 跳过适配（可选组件） |
| Compression shared_store | **无降级**——shared_store 由 `main.rs` 在服务启动前创建并传递 | 找不到 → 编译期/启动期报错 |
| Chronos ExecuteTool | **无降级**——ToolsService 先于 Chronos 启动，`PROVIDER_TOOL` 保证存在 | 找不到 → `Err` 启动失败 |
| Memory 3 子服务 | **无降级**——方法体中直接实现调用 | 实现即用，无退化状态 |
| BlockCollector 排序 | **无降级**——`sort_by_key` 是确定性操作 | 始终成功 |
