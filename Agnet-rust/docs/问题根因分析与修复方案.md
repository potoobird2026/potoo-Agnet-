## 第一部分：全局判断

### 1.1 当前项目状态

```
  协议文档定义层     ──── 完整，但存在一处遗漏
       ↓
  插件代码实现层     ──── 外壳完整，内部存在系统性 gaps
       ↓
  集成连接层         ──── 多处断裂（wiring 未完成）
       ↓
  运行时验证层       ──── 完全缺失（tests/ 为空）
```

**核心结论**：项目经历了"分层开发"（不同 AI/开发者负责不同模块），但缺少了一个关键的**集成验收环节**。这不是简单的代码 bug，而是**开发流程中缺少了一个"I 型"环节**——每层各自的代码都"看起来对"，但层与层之间的对接没有验证。

### 1.2 问题的根因分类

| 根因类型 | 涉及问题数 | 本质 |
|:---------|:----------|:-----|
| **A 类：集成连接缺失**（Wiring Gap） | 6 个 | 组件/服务的基础设施已开发完成，但未被串联进业务流程 |
| **B 类：占位符未替换**（Placeholder Leftover） | 5 个 | 开发初期留下的 `Arc::new(())` 从未被替换为真实实现 |
| **C 类：文档-代码对不齐**（Doc-Code Drift） | 4 个 | 协议文档的要求与实际代码行为不一致 |
| **D 类：Rust 语言限制**（Language Limitation） | 1 个 | `unsafe transmute` 属于 Rust 自身 trait 对象系统的限制 |

## 第二部分：逐一深度分析

### 问题 #9 — P0 compression `run_loop` 不调用 compress()

#### 现象

`CompressionService::run_loop()`（`service.rs:157-177`）监听 `HookEvent::NewMessagesArrived`，收到后只做状态切换：
```
Sleep → Compressing → Sleep
```
**从未调用** `inner.compressor.compress()` 或任何其他压缩组件（`pid`、`token_counter`、`scorer`、`ucb` 等）。

#### 证据

```rust
// service.rs:168-174 —— run_loop 中唯一的 "压缩" 逻辑
Ok(HookEvent::NewMessagesArrived { session_id }) => {
    if inner.state == ServiceState::Sleep {
        inner.state = ServiceState::Compressing;
        tracing::info!("Compression: 开始压缩 session={}", session_id);
        // 压缩算法由主循环驱动，此处仅状态转换
        inner.state = ServiceState::Sleep;  // ← 状态立即回到 Sleep，什么都没做
    }
}
```

但 `compressor.rs:14-45` 中的 `Compressor::compress()` 有完整实现（摘要生成、token 节省计算）。`services/mod.rs:14` 也定义了 12 个完整的业务 trait 接口。

#### 根因分析

| 维度 | 分析 |
|:----|:-----|
| **是文档还是代码？** | **代码**。协议文档（`protocol-Slot接入协议.md` §2.2/§7）明确要求 Service 的 Provider 注册真实能力，但代码未执行。文档无问题。 |
| **哪个环节脱节？** | **集成连接环节（Wiring）**。compression 模块分三层：(1) `components/` 中 12 个业务组件（基础设施层）；(2) `services/mod.rs` 中 12 个业务 trait（接口层）；(3) `service.rs` 中的 `run_loop`（驱动层）。第(1)(2)层完成，第(3)层只建了**空骨架**——事件循环知道"什么时候压缩"但不知道"怎么压缩"。 |
| **为什么会导致？** | 开发者 A 完成了 compression 的组件基础设施（Compressor、PidController、Scorer 等），开发者 B 完成了 ServicePlugin 外壳（init、start、run_loop），但 **A 和 B 之间没有约定的对接接口**——B 不知道 run_loop 里应该调用 A 的什么组件。代码中的注释"压缩算法由主循环驱动"是**把责任推给未来**的典型模式。 |
| **违反了什么协议？** | `protocol-Service集成协议.md` §2.2："`start`：在此方法中调用 `register_provider()` 注册能力，然后启动后台循环"——**本服务注册了 `Arc::new(())` 而不是压缩能力，且后台循环实际不执行其声称的职责**。`protocol-Slot接入协议.md` §7 也要求 Provider 在运行时可用且功能完整。 |

#### 修复方案

**方案（系统性，非打补丁）**：在 `run_loop` 中集成完整的压缩管道。

```
NewMessagesArrived
 → inner.shared_store.read(session_id)     // 获取消息
 → inner.token_counter.count(messages)     // 计数
 → inner.scorer.score(...)                 // 逐条评分
 → inner.ucb.decide(...)                   // 决定保留/压缩
 → inner.pid.update(...)                   // 自适应调整目标
 → inner.compressor.compress(...)          // 执行压缩摘要
 → inner.shared_store.write(session_id, compressed)  // 写回
```

**是否影响其他模块？**：无影响。compression 是独立后台服务，与 Pipeline 解耦。`run_loop` 中的改动完全在 `CompressionService` 内部。

**更好的方案？**：是，可以引入一个 `CompressionOrchestrator`（与 chronos 的 `ChronosOrchestrator` 对标），将上述 6 步封装为 `process_all()`。但这不是必须的——12 个组件数量可控，直接顺序调用即可。

### 问题 #10 — P0 chronos `ActionExecutorComponent::execute()` 只返回计数

#### 现象

```rust
// action_executor.rs:18-26
async fn execute(&self, decision: &Decision, _task_queue: &dyn TaskQueueService) -> Result<usize, String> {
    match decision {
        Decision::Execute { actions } => {
            let count = actions.len().min(self.config.max_concurrent_actions);
            // 任务执行由主循环驱动，这里标记执行状态
            Ok(count)  // ← 只返回个数，不执行任何 action
        }
        Decision::Skip { .. } => Ok(0),
        Decision::Escalate { .. } => Ok(0),
    }
}
```

#### 根因分析

| 维度 | 分析 |
|:----|:-----|
| **是文档还是代码？** | **代码 + 文档双重问题**。`chronos开发文档.md` 描述了 ActionExecutorComponent 的职责（"执行提醒、维护、主动发起等动作"），但没有定义执行的具体算法。代码中的注释"任务执行由主循环驱动"将实现推迟到了 chronos 主循环。但主循环（`run_loop`）也从未调用 `action_executor.execute()`——它在 `ChronosOrchestrator::process_all()` 中也是个空操作。 |
| **哪个环节脱节？** | **组件集成与测试环节**。Chronos 的组件层（init/process/shutdown）和业务服务层（ActionExecutorService）之间存在**接口不兼容**——Component 的 `process(&mut self, _ap: &mut dyn InternalAccessPoint)` 接受 `InternalAccessPoint`，而 ActionExecutorService 的 `execute()` 接受 `(decision, task_queue)`，两者互不调用。开发者没有决定"谁驱动谁"——是 Component 的 process() 包装 execute()，还是 Orchestrator 直接调用 execute()。 |
| **为什么会导致？** | Chronos 引入了两套体系：`Component` trait（core 级的通用编排接口）和 `ActionExecutorService` trait（chronos 内部的业务接口）。两套体系各有其生命周期，但没有桥接。注释"Component trait 对象与业务 trait 分离"是故意为之的架构决定，但**没有完成桥接代码**。 |
| **违反了什么协议？** | 不直接违反协议，但违反 `开发插件完整流程.md` Red Line #5："每个插件必须实现完整生命周期——init/run(或start)/shutdown 都要能正常执行"。`execute()` 的语义是"执行动作"，但实际不做任何事情，违反了"名副其实"的基本代码原则。 |

#### 修复方案

**方案（系统性）**：选择一种架构策略并完全实现。

**策略 A（推荐）**：放弃 Component 双体系，让 Orchestrator 直接调用业务服务。

```rust
// ChronosOrchestrator 中，在决策引擎产生 Decision 后：
let executed = self.action_executor.execute(&decision, &self.task_queue).await?;
```

然后在 `ActionExecutorComponent::execute()` 中实现真实的动作执行：
```rust
Decision::Execute { actions } => {
    let count = 0;
    for action in actions.iter().take(self.config.max_concurrent_actions) {
        match self.tool_bridge.call(&action.tool, &action.args).await {
            Ok(result) => { count += 1; /* 记录到 task_queue */ }
            Err(e) => { /* 记录错误 */ }
        }
    }
    Ok(count)
}
```

**策略 B**：让 Component::process() 封装 execute()，通过 InternalAccessPoint 参数传递 `(decision, task_queue)`。

**影响范围**：仅 chronos 模块内部。需要 `ActionExecutorComponent` 持有 `tool_bridge` 或 `ToolProvider` 引用（通过 Provider 机制获取）。

### 问题 #11/#15-#19 — 5 处 `Arc::new(())` 假 Provider

#### 现象

5 个 ServicePlugin 的 `start()` 都注册了空元组：

| Service | Key | 代码位置 | 应注册 |
|:--------|:----|:---------|:-------|
| Skills | `"skills"` | `skills/service.rs:44` | `SkillInjectionProvider`（有完整实现） |
| Memory | `"vector"` | `memory/service.rs:72` | 向量检索能力 |
| Chronos | `"chronos"` | `chronos/service.rs:133` | 调度/定时能力 |
| CLI | `"cli_channel"` | `cli/plugin.rs:41` | CLI 通道能力 |
| Compression | `"compression"` | `compression/service.rs:77` | 压缩能力 |

#### 根因分析

| 维度 | 分析 |
|:----|:-----|
| **是文档还是代码？** | **代码**。协议文档 `protocol-Service集成协议.md` §2.2 给出了正确的注册示例（`register_provider("memory", Arc::new(L2Memory{...}))`），但代码没照着做。 |
| **哪个环节脱节？** | **需求定义环节**。这些 Provider key 的注册属于"存在性注册"——没有其他 Slot 通过 `provider_raw("skills")` 来找 `SkillsService` 的能力（没有任何 Slot 的代码搜索 `"skills"` key）。注册这些 key 只是为了**让 `register_provider()` 被调用过**，凑齐"服务已注册"的证据。既然没有消费者，自然也不会有人关心注册了什么。 |
| **为什么会导致？** | 五个服务的 `Arc::new(())` 都是同一个模式：初期搭建时，知道"Service 需要注册 Provider"，但**当时还没有消费方需要这些能力，于是放了占位符**。项目迭代中，始终没有 Slot 去 `provider_raw("chronos")`、`provider_raw("skills")`、`provider_raw("compression")`、`provider_raw("vector")`、`provider_raw("cli_channel")`——因为没有消费者需求，所以占位符从未被替换。 |
| **违反了什么协议？** | **违反 `protocol-Service集成协议.md` §2.2 的语义**。"provides" 在元数据中列出的能力应当是真实可用的。`protocol-shared_types契约协议.md` §7 检查清单要求"impl 存在"——虽然不涉及编译报错，但违反了"提供真实能力"的契约精神。 |

#### 修复方案

**方案（整体性）**：确定每个假 Provider 是否存在真实消费者，分两类处理：

**A 类 — 无消费者，删除注册**：
- `"skills"`：`SkillInjectionProvider` 可以在 `init()` 中加载、在 `start()` 中注入系统消息（通过 `Runtime` 的 system message 队列），不需要通过 Provider 机制。**删除 `register_provider("skills", ...)` 行**。
- `"cli_channel"`：CLI 是入口通道，其他插件不需要查找 CLI Provider。**删除该注册行**。
- `"chronos"`：如果需要让其他模块查看 Chronos 状态，才创建真正的 `ChronosProvider` trait。否则**删除该注册行**。
- `"compression"`：同上，有需求再创建 Provider。**删除该注册行**。

**B 类 — 有消费者，实现真实 Provider**：
- `"vector"`：MemoryService 的 L3 向量检索当前使用 `NoopEmbeddingModel`。可以保留 `Arc::new(())` 直到 L3 的 embedding 实现完成后再替换，或将其改为 `ap.register_provider("vector", Arc::new(DynProvider(real_vector_provider)))`。

**影响范围**：仅删除 `register_provider()` 行，不影响其他代码。无消费者意味着不会有任何 `provider_raw()` 返回 None。

### 问题 #20 — Slot 未调用 `init()`（加 ToolExecutorSlot 额外发现）

#### 现象

`main.rs:108-114` 中，3 个 Slot 通过 `add_slot(Box::new(Slot::new()))` 直接注册：

```rust
Pipeline::with_recommended_phases()
    .add_slot(Phase::init(), Box::new(InitPhaseSlot::new()))        // ❌ 无 init()
    .add_slot(Phase::context(), Box::new(ToolRegistrySlot::new()))  // ❌ 无 init()
    .add_slot(Phase::execute(), Box::new(ToolExecutorSlot::new()))  // ❌ 无 init()
    // ✅ 以下 4 个有 init()：
    .add_slot(Phase::think(), Box::new(llm_slot))                   // llm_slot.init() 已调用
    .add_slot(Phase::audit(), Box::new(audit_slot))                 // audit_slot.init() 已调用
    .add_slot(Phase::loop_phase(), Box::new(react_loop_slot))       // react_loop_slot.init() 已调用
    .add_slot(Phase::memorize(), Box::new(memory_saver_slot))       // memory_saver_slot.init() 已调用
```

#### 根因分析

| 维度 | 分析 |
|:----|:-----|
| **是文档还是代码？** | **文档引发 + 代码不一致**。`开发插件完整流程.md` 的 Step 4 示例代码：`Pipeline::with_recommended_phases().add_slot(Phase::think(), Box::new(MySlot))`——同样没有调用 `init()`。这个示例**误导了后续开发**。而 `main.rs` 本身也不一致——4 个 slot 调了 `init()`，3 个没调。 |
| **哪个环节脱节？** | **文档与代码模板环节**。`protocol-Slot接入协议.md` §6 明确定义了生命周期：`init → run (多次) → shutdown`，且 S-R02 规定 "init 失败意味着插件不被加载"。但 Pipeline 的 `add_slot()` 不调用 `init()`，`run()` 也不调用 `init()`。**init() 的调用责任完全交给了 main 函数**。文档示例和 main.rs 部分代码都没有履行这个责任。 |
| **为什么会导致？** | 回顾 main.rs 的演进：最初只有 `llm_slot` + `react_loop_slot`（有 init()）。后来逐步添加 `audit_slot`、`memory_saver_slot`（也调了 init()），但 `InitPhaseSlot`、`ToolRegistrySlot`、`ToolExecutorSlot` 是在**批量添加阶段**一次性 `add_slot(Box::new(XxxSlot::new()))` 加进来的，当时没有遵从"先 init 再 add_slot"的模式。 |
| **违反了什么协议？** | **违反 `protocol-Slot接入协议.md` §6 生命周期**和 **S-R02**（init 失败意味着插件不加载）。`InitPhaseSlot` 的 init() 必须调用否则 `self.config=None` → run() 返回 Continue→**整个初始化阶段静默跳过**。`ToolExecutorSlot` 的 init() 必须调用否则 `self.orch=None` → run() 报 **运行时错误**。`ToolRegistrySlot` 的 init() 是空操作，错过无影响。 |

#### 影响分析

| Slot | init() 调用位置 | 实际后果 |
|:-----|:---------------|:---------|
| `InitPhaseSlot` | init() 解析配置、设置 `self.config` | ❌ `run()` 中 `self.config` 为 None → 返回 Continue → **初始化阶段不执行任何操作**（不加载记忆、不组装 system prompt、不预检上下文窗口） |
| `ToolExecutorSlot` | init() 创建 Orchestrator、注册 2-3 个组件、调用 `init_all()` | ❌ `run()` 中 `self.orch.as_mut()` 返回 None → 返回 `PluginError::Runtime("tool_executor: 未初始化")` → **整个 execute 阶段崩溃** |
| `ToolRegistrySlot` | init() 是空操作 | ✅ 无影响 |

#### 修复方案

**方案（系统性）**：修复 `main.rs`，对 3 个缺失 init() 的 Slot 补充调用。

```rust
// InitPhaseSlot
let mut init_slot = InitPhaseSlot::new();
let init_ctx = PluginInitContext::new("init_phase", /* config */, ...);
init_slot.init(&init_ctx).await.map_err(...)?;

// ToolRegistrySlot (init 是空操作，但为一致性仍需调用)
let mut tool_registry_slot = ToolRegistrySlot::new();
let tool_registry_ctx = PluginInitContext::new("tool_registry", /* config */, ...);
tool_registry_slot.init(&tool_registry_ctx).await.map_err(...)?;

// ToolExecutorSlot
let mut tool_executor_slot = ToolExecutorSlot::new();
let tool_executor_ctx = PluginInitContext::new("tool_executor", /* config */, ...);
tool_executor_slot.init(&tool_executor_ctx).await.map_err(...)?;
```

**更好的方案**：修改 `Pipeline::add_slot()` 使其在内部调用 `init()`。但这样做需要 `add_slot` 接受 `&PluginInitContext`，会改变其签名。更简洁的方案是**在 main.rs 中统一风格**——所有 slot 在 add_slot 前调用 init()。

**影响范围**：仅 `main.rs`，不涉及其它模块。但修复此问题后，`InitPhaseSlot` 会真正开始工作，这会暴露 Memory Provider 是否正确注册的连锁问题（当前已正确注册，预计无阻）。

### 问题 #13 — llm_thinker 的 `unsafe transmute`

#### 现象

实际代码中只有 **2 处**（非用户声称的 5 处）：

1. `llm_thinker/component.rs:86`：
```rust
unsafe { std::mem::transmute(comp_box) }
// Box<dyn Component> → Box<dyn ComponentHandle> 的 vtable 指针转换
```

2. `llm_thinker/orchestrator.rs:95`：
```rust
let handle: Box<dyn ComponentHandle> = unsafe { std::mem::transmute(cloned) };
// 同上转换
```

#### 根因分析

| 维度 | 分析 |
|:----|:-----|
| **是文档还是代码？** | **Rust 语言限制**。这不是代码质量或文档问题。Rust 不允许在不同的 trait 对象之间安全地进行 vtable 转换，即使存在 `impl<T: Component + 'static> ComponentHandle for T` 的 blanket impl。编译器不跟踪 trait 之间的实现关系。 |
| **哪个环节脱节？** | **架构设计与 Rust 类型系统的冲突**。项目引入了 `Component` + `ComponentHandle` 双 trait 模式来绕过一个 Rust 的对象安全限制：`Box<dyn Component>` 需要 `Component: Clone`（不能是 trait 方法）但 `Component` 的 `process()` 接受 `&mut dyn InternalAccessPoint`（使用 `dyn`，已经是对象安全的）。但 `ComponentHandle` 为了与 `InternalAccessPoint` 兼容，要求 `clone_box()` 返回 `Box<dyn ComponentHandle>`——而 `Box<dyn Component>` 和 `Box<dyn ComponentHandle>` 在运行时的 vtable 布局不同，需要 unsafe transmute。 |
| **为什么会导致？** | 设计者选择了这种双 trait 模式以便 `InternalAccessPoint` 内部存储 `HashMap<String, Box<dyn ComponentHandle>>`——如果只用 `Component`，`clone_box()` 返回 `Box<dyn Component>` 但存储时需要 `Box<dyn ComponentHandle>`，同样需要 transmute。这是 Rust 在 2024 年（编写时）还没有稳定 trait upcasting 的折中方案。 |
| **违反了什么协议？** | 不违反任何协议。`unsafe` 有详细的 soundness 注释和论证。但 `protocol-Slot接入协议.md` 和 `开发插件完整流程.md` 没有对 `unsafe` 的使用做任何规定——这是一个文档空白。 |

#### 修复方案

**方案（系统性）**：当 Rust 的 trait upcasting 稳定后（预计 2025+），`unsafe transmute` 可以被移除。当前唯一的选择是使用 `trait_upcasting` feature（nightly-only）或使用 `std::ptr::read`/`std::ptr::write` 的替代方案，但这不能消除 `unsafe`。

**当前务实做法**：保留两处 `unsafe`，但添加自动化验证（miri 或 loom）确保 transmute 的 soundness 在 CI 中被检查。

**影响范围**：无。这是内部实现细节，不暴露给外部。

### 问题 #5 — MCP StdioMcpConnector stdin/stdout 未保存（假阳性）

#### 分析

原问题称"stdin/stdout 未保存，连接无法复用"。实际检查代码后：

```rust
// connector.rs:71-76
let child = self.child.as_mut().ok_or("MCP Server 未连接")?;
let stdin = child.stdin.as_mut().ok_or("stdin 不可用")?;    // ← 每次从 child 获取
let stdout = child.stdout.as_mut().ok_or("stdout 不可用")?;  // ← 每次从 child 获取
```

`tokio::process::Child` 的 `stdin` 和 `stdout` 是**公有字段**（`pub stdin: Option<ChildStdin>`），不是一次性方法。`.as_mut()` 可以反复调用。**每次 `send_request()` 都从 `child` 中获取 stdin/stdout 的 `&mut` 引用，这是正确且可复用的**。

**结论：此条为误报。** `StdioMcpConnector` 的连接管理逻辑正确，所有请求共享同一个子进程的 stdin/stdout。

#### 假阳性的原因

在项目早期版本中，可能 `child.stdin` 和 `child.stdout` 被 `.take()` 移出（`Option::take()`），导致第二次调用时返回 None——`send_request` 中的 `.ok_or("stdin 不可用")` 会触发错误。检查当前代码，使用的是 `.as_mut()` 而非 `.take()`，**代码已被修复或从未有过此问题**。

### 问题 #7 — ToolDefinition 两处定义

#### 现象

| 位置 | 定义 |
|:----|:-----|
| `src/shared_types/tool.rs:14-19` | `pub struct ToolDefinition { name, description, parameters, entry }` 带 `#[derive(Debug, Clone, Serialize, Deserialize)]` |
| `src/plugins/services/tools/registry.rs:14` | `pub struct ToolDefinition { name, description, parameters, entry }` 带 `#[derive(Debug, Clone)]` 无 serde |

#### 根因分析

| 维度 | 分析 |
|:----|:-----|
| **是文档还是代码？** | **代码**。`protocol-shared_types契约协议.md` 第 6 节明确列出 `ToolDefinition` 在 shared_types 中定义。`开发插件完整流程.md` Step 2 也要求"跨插件数据结构必须定义在 shared_types"。registry.rs 中的第二定义是**重复定义**，违反了 T-R01（trait 不在 services 内部定义）的延伸原则——结构体也不应在 services 内部重复定义。 |
| **哪个环节脱节？** | **代码维护环节**。`shared_types/tool.rs` 中的 `ToolDefinition` 是后来新增的（协议文档规定后）。registry.rs 中的 `ToolDefinition` 是历史遗留，当时还没有 `shared_types`。后来加入 shared_types 时，应该删除 registry.rs 中的重复定义并用 `use crate::shared_types::ToolDefinition as SharedToolDef` 替代，但开发者只添加了 `as SharedToolDef` 的 use 语句，**没有删除原始定义**。 |
| **为什么会导致？** | registry.rs 内部有 6 处直接引用本地的 `ToolDefinition`（作为 `HashMap` 值类型、`register()` 参数、`get()` 返回类型等）。删除本地定义需要同时修改所有引用。开发者选择了"添加别名并实现转换"的**最小改动路径**，以避免大规模重构。 |

#### 修复方案

**方案（系统性）**：删除 registry.rs 中的本地 `ToolDefinition`，全局使用 shared_types 的版本。

```rust
// registry.rs —— 删除第 14 行的本地 struct 定义，改为 use：
use crate::shared_types::ToolDefinition;

// 将 HashMap 的值类型从 Arc<ToolDefinition> 改为 Arc<ToolDefinition>（相同名称，无需改动）
// 删除 ToolProvider impl 中的逐字段转换（直接从 Arc::new(local_def) 改为 Arc::new(shared_def)）
```

**影响范围**：`registry.rs` 内部，6 处引用 + `ToolProvider impl` 中的转换代码。无外部影响因为其他地方都引用 shared_types 版本。

### 问题 #12 — chrono::DateTime 与 Timestamp 混用

#### 现象

9 处 `use chrono` 分布在：
- chronos：5 处（`service.rs`、`types.rs`、`components/mod.rs`、`task_queue.rs`、`state_encoder.rs`）
- memory：4 处（`l1_identity/manager.rs`、`l2_working/forgetting.rs`、`l2_working/manager.rs`、`l3_vector/sync.rs`）

#### 根因分析

| 维度 | 分析 |
|:----|:-----|
| **是文档还是代码？** | **两者都不是——模块独立性**。chronos 和 memory 各自在自己的模块内部使用 `chrono::DateTime<Utc>` 作为时间类型。这是它们内部实现的选择。`core::types::Timestamp` 是核心层时间类型，但不强制插件使用。协议文档没有规定插件内部必须使用什么时间类型。 |
| **哪个环节脱节？** | **没有脱节**——这只是类型不统一，但不导致功能问题。两个系统各自运作，没有强制要求统一。 |
| **为什么会导致？** | chronos 模块开发时直接使用了 `chrono` crate（已在 `Cargo.toml` 中），因为它的时间运算更丰富。核心的 `Timestamp` 基于 `std::time::Instant` 和 `SystemTime`，功能较简单。开发者选择了更适合业务需求的类型。 |
| **违反了什么协议？** | 不违反任何协议。协议文档不约束模块内部实现。 |

#### 修复方案

**不修复**。这是"统一的审美偏好"而非"功能问题"。如需统一，需将 `core::types::Timestamp` 扩展为包含 `chrono::DateTime<Utc>` 的包装，然后逐步迁移。这不是 P0/P1 问题。

## 第四部分：系统性改进建议

### 4.1 在协议层面补充

**协议缺失 1**：`protocol-Slot接入协议.md` 没有明确 **`init()` 的调用方**。§6 生命周期的图表显示 `init → run → shutdown`，但没说"由 main 函数调用"。建议在 §6 中增加：

> **生命周期责任**：`init()` 由插件加载方（通常是 `main.rs`）在将 Slot 注册到 Pipeline 之前调用。Pipeline 不负责调用 `init()`。如果 init() 未在 main.rs 中被调用，Slot 的 `run()` 必须以退化模式运行（如 `PluginError::Runtime`）以暴露此问题。

**协议缺失 2**：`protocol-Service集成协议.md` §2.2 应增加红线：

> P-R01：`register_provider()` 的第二个参数禁止传递 `Arc::new(())`——空元组不是合法的 Provider。如果本服务当前没有可注册的能力，则不调用 `register_provider()`。

### 4.2 增加自动化校验

当前的"Provider 对接检查清单"（`开发插件完整流程.md` Step 8）是人工执行的。建议增加一个自动化脚本：

```bash
# 检查所有 register_provider 调用
grep -rn "register_provider.*Arc::new(())" src/
# → 如果有输出，说明存在假 Provider，CI 失败
```

### 4.3 整体修复路径

```
Step 1: main.rs 补充 3 个 Slot 的 init()           ← 修完即可运行，不会立即崩溃
Step 2: 删除 5 处 Arc::new(()) 注册                  ← 清理架构
Step 3: compression run_loop 接入组件                 ← 让压缩真正工作
Step 4: chronos action_executor 实现执行逻辑          ← 让定时调度真正工作
Step 5: 删除 registry.rs ToolDefinition 重复定义     ← 清理技术债务
Step 6: 更新协议文档（init() 调用方 + Arc::new(()) 红线） ← 防止重复发生
```
