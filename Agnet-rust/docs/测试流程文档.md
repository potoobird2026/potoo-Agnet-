# aagnet 测试流程文档

> 版本：v1.0
> 适用对象：AI 开发者 + 人工审核
> 原则：不破坏源码，零风险加测试

---

## 一、测试体系结构

```
aagnet 测试体系
├── 单元测试                  #[cfg(test)] 内嵌在 src/*.rs 中
│   ├── 白盒测试              直接测试内部函数、结构体方法
│   ├── Mock SlotAccessPoint  模拟 Slot 接入点（关键依赖）
│   └── Mock Provider         模拟 Service 能力
│
├── 集成测试                  tests/*.rs（独立目录，不影响 src）
│   ├── Pipeline 流程测试      从 StepInput 到 StepResponse 的全链路
│   ├── Provider 对接测试      验证 register/downcast 类型匹配
│   └── Assembler 组装测试     验证 Token 预算/配额分配/消息拼装
│
└── CI/CD                     GitHub Actions（.github/workflows/ci.yml）
    ├── cargo check           编译检查
    ├── cargo test            运行全部测试
    └── cargo clippy          代码规范检查
```

## 三、单元测试规范

### 3.1 通用模板

```rust
#[cfg(test)]
mod tests {
    use super::*;

    // ── Mock SlotAccessPoint ──
    // 每个需要测试 SlotPlugin 的模块，都需要实现一个最小 MockAccessPoint

    struct MockAccessPoint {
        messages: Vec<Message>,
        context_data: HashMap<String, Box<dyn Any + Send + Sync>>,
        providers: HashMap<String, Arc<dyn Any + Send + Sync>>,
    }

    impl MockAccessPoint {
        fn new() -> Self {
            Self {
                messages: vec![],
                context_data: HashMap::new(),
                providers: HashMap::new(),
            }
        }
    }

    impl SlotAccessPoint for MockAccessPoint {
        fn messages(&self) -> &[Message] { &self.messages }
        fn session_id(&self) -> &str { "test-session" }
        fn phase_name(&self) -> &str { "test" }
        fn current_iteration(&self) -> usize { 1 }
        fn write_observation(&mut self, _obs: Box<dyn Any + Send + Sync>) -> Result<(), PluginError> { Ok(()) }
        fn write_context_raw(&mut self, key: &str, val: Box<dyn Any + Send + Sync>) -> Result<(), PluginError> {
            self.context_data.insert(key.to_string(), val);
            Ok(())
        }
        fn read_context_raw(&self, key: &str) -> Option<&(dyn Any + Send + Sync)> {
            self.context_data.get(key).map(|b| b.as_ref())
        }
        fn request_jump(&self, _phase: &str) -> Result<(), PluginError> { Ok(()) }
        fn request_abort(&self) -> Result<(), PluginError> { Ok(()) }
        fn provider_raw(&self, name: &str) -> Option<Arc<dyn Any + Send + Sync>> {
            self.providers.get(name).cloned()
        }
    }
}
```

### 3.2 测试结构规范

```
每个测试遵循 AAA 模式：
   Arrange（准备数据）→ Act（调用被测函数）→ Assert（验证结果）

测试命名：
   test_{被测功能}_{场景}_{期望结果}
   例：test_budget_computation_when_large_context_returns_correct_budget
```

### 3.3 强制规则

| # | 规则 |
|:-:|:-----|
| 1 | 测试中禁止使用 `unwrap()` —— 用 `expect("原因")` |
| 2 | 所有 Mock 的未使用参数填默认值，不要 `todo!()` |
| 3 | 每个 `#[cfg(test)] mod tests` 至少包含一个正向测试 + 一个降级测试 |
| 4 | `std::env::temp_dir()` 用于临时路径，禁止硬编码 `/tmp/` |
| 5 | 测试不依赖真实 Service（不使用 `provider_raw` 返回真实 Provider） |
| 6 | 测试不写文件系统（DocumentCompactor 测试除外） |

## 四、运行测试

### 4.1 只运行编译检查（最快）

```bash
# 不运行测试，只检查编译
cargo check

# 包含测试代码的编译检查
cargo check --tests
```

### 4.2 运行全部测试

```bash
cargo test
```

### 4.3 只运行特定模块的测试

```bash
# 只运行 assembler 模块的测试
cargo test --lib assembler

# 只运行包含特定关键字的测试
cargo test budget

# 只运行 DocumentCompactor 测试
cargo test compact
```

### 4.4 只运行集成测试

```bash
# 只运行 tests/ 目录下的集成测试
cargo test --test test_assembler

# 运行所有集成测试
cargo test --test '*'
```

### 4.5 查看测试输出

```bash
# 显示 println! 输出
cargo test -- --nocapture

# 显示所有测试名（通过的也显示）
cargo test -- --show-output
```

## 五、CI/CD 配置（GitHub Actions）

在项目根目录创建 `.github/workflows/ci.yml`：

```yaml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

env:
  CARGO_TERM_COLOR: always

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - name: Rust 工具链
      uses: actions-rust-lang/setup-rust-toolchain@v1
    - name: cargo check
      run: cargo check --all-targets
    - name: cargo test
      run: cargo test
    - name: cargo clippy
      run: cargo clippy --all-targets -- -D warnings
```

## 六、执行顺序

```
阶段 1（修复 pre-existing）
  ├── 修复所有 #[cfg(test)] 中的编译错误
  ├── 确认 cargo test --lib 编译通过
  └── 确认 cargo test --lib 测试通过

阶段 2（Assembler 单测）
  ├── 为 DocumentCompactor 写单测（已存在 4 个，补全）
  ├── 为 BudgetCalculator 写单测
  ├── 为 QuotaAllocator 写单测（不依赖 Mock AP）
  ├── 为 BlockCollector 写单测（需要 Mock AP）
  ├── 为 AssemblerSlot 写单测（Mock AP + 生命周期）
  └── 确认 cargo test --lib assembler 全部通过

阶段 3（集成测试）
  ├── tests/test_assembler.rs（完整 Pipeline 流程）
  ├── tests/test_provider_downcast.rs（Provider 类型匹配）
  └── 确认 cargo test 全部通过

阶段 4（CI/CD）
  ├── .github/workflows/ci.yml
  ├── 推送到 GitHub 验证 Actions 通过
  └── 以后每次 PR 自动运行
```

## 七、常见问题

### Q: 测试代码会影响正式编译的性能吗？
A: 不会。`#[cfg(test)]` 标记的代码在 `cargo build --release` 中**完全不存在**。

### Q: `tests/` 目录和 `src/` 会冲突吗？
A: 不会。`tests/` 下的文件独立编译，不参与 `src/` 编译。

### Q: Mock 实现要写很多样板代码怎么办？
A: 每个测试模块只需要一个 MockAccessPoint，可以复制上面的模板。建议未来用 `mockall` crate 自动生成。

### Q: 如何验证测试覆盖了所有分支？
A: `cargo tarpaulin`（需要安装）或 `cargo llvm-cov` 可生成覆盖率报告。
